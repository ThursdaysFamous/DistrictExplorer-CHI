Ships the Data gaps panel — the app's inventory of what it cannot answer, and the source-submission path that invites readers to close it. **Three NEW blocks**, so this release needs sibling fence seeding (see below) before its bump PRs can merge.

- **New `coverage-gaps`**: reads `data/app/coverage-gaps.json` and renders the panel. Location-aware — with a point selected it leads with the gaps that apply *there*, tested against the `<slug>-county-outline.json` files a fork already ships for its coverage tests. Every gap offers a prefilled GitHub issue-form link, so the reporter never copies an identifier by hand.
- **New `gaps-html`**: the footer trigger button.
- **New `gaps-modal-html`**: the panel markup. Reuses the feedback modal's shell classes rather than introducing a second modal idiom; only the width and the list inside are new (those styles are additions to the existing `styles-footer` block, not a fourth new block).

**Adopting fork requirements.** Two, and the first is mandatory before the bump:

1. **Seed the three fence pairs** (`gaps-html`, `gaps-modal-html`, `coverage-gaps`) at the reference placement — button beside the feedback button in the footer, modal after the feedback modal, JS immediately before the `feedback` block. `apply_engine.py` fills existing fences only; without the pairs the bump fails with "index.html is missing ENGINE block(s) the manifest requires".
2. **Supply `data/app/coverage-gaps.json`**, keyed by gap id, and register it in the worksheet's roster list. The block degrades honestly without it — the panel shows "couldn't load the gap list" — but a fork shipping the button with no data is worse than not shipping the button, so seed the file in the same PR. Chicago generates it from a `GUIDEBOOK:BEGIN gaps` block via `scripts/build_coverage_gaps.py`, whose `--check` is the drift gate; a fork can adopt the same block (add its metro key) or author the file directly.

**The new-block trap, now recorded in both directions.** `docs/ENGINE_SYNC.md` already warned that a release shipping new blocks breaks *sibling* bumps until their fences are seeded ("missing ENGINE block(s) the manifest requires"). This release found the mirror image the hard way: adding a new block breaks **the reference fork's own deploy** the moment it merges, because `apply_engine.py` splices the *pinned* release and fails with "index.html has ENGINE block(s) the manifest does not know". Nothing in PR CI catches it — `check_engine_parity.py` lints Chicago's fences against Chicago's file and is perfectly happy; the assemble step is the first thing that compares them to the pinned manifest. So a new block is not shippable in one PR: the block lands, the deploy fails, and the release that ships it is what repairs the deploy. Cut the release in the same sitting.
