Second and final correction to v1.0.16's adoption break. **The engine bundle is byte-identical to v1.0.16 and v1.0.17** — same `sha256 13e3ffa0a213`, same 50+2 blocks, no JS change in any of the three. Only `generate_metro_files.py` moves.

- **Changed `generate_metro_files.py`**: `POI_GEOCODE_BBOX` is emitted **only when the worksheet declares `poi_geocode_bbox`**. A fork that doesn't declare it gets a metro-config region byte-identical to the pre-key generator — verified by rendering both and comparing.

**Why v1.0.17 wasn't enough.** v1.0.17 made the key optional and defaulted the value to `metro_bbox`, which fixed schema validation — and then failed the siblings a second time, one gate later:

```
generate-metro-files: FAIL — 1 region(s) drifted from the worksheet.
```

The consumer `engine-bump.yml` applies the release and copies the shared scripts **but never runs the generator**; it only validates afterwards. So a generator emitting a new line — even one whose *value* reproduces the old behaviour — puts every sibling's `index.html` out of sync with its own worksheet, and the drift gate fails the bump PR.

**The rule, now stated correctly.** "Default to the old value" is too weak. **A shared-script change must be inert in a fork that has not opted in — byte-identical output, not merely equivalent behaviour.** Gate any new emitted line behind `if "<key>" in w:` and keep the key optional. Neither failure mode is observable from Chicago: Chicago's worksheet carries whatever the change needs, so its own gates stay green, and the release job's self-checks exercise the bundle, which never reads a worksheet. Recorded in `docs/ENGINE_SYNC.md` under the tooling section.

The eventual structural fix is for `engine-bump.yml` to regenerate after applying, which would make generator changes safe by construction. That file lives in the sibling repos, so it is a coordinated change rather than a Chicago one, and is left as the open item.

For adopters this release is a no-op beyond the lockfile: no worksheet edit, no regeneration, no behaviour change. The v1.0.16 guidance is unchanged and still worth acting on — `poiGeocodeRequest` is fork-level code, and its bound belongs to the widest layer the fork ships, not to its metro. Declare `poi_geocode_bbox` if and when a layer reaches past the metro; until then nothing is emitted and nothing changes.
