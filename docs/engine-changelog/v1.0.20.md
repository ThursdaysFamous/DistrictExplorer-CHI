Fixes a line in the Data gaps panel that could claim something untrue in a fork with no county outlines. **One changed block, no new blocks** — adopting forks need no fence seeding.

- **Changed `coverage-gaps`**: the "nothing here" section heading now requires that some gap was *mappable* in the first place. Previously, selecting a point with no matching gaps always produced **"Nothing missing where you clicked — elsewhere:"**. That is true for Chicago, whose gaps are county-tagged: an unmatched point genuinely has none of them. It is **false** for a fork that tags no gap with a county — NYC's and SF's gaps all apply fork-wide, so the line told a reader their location was clean while listing three gaps that cover it. Those forks now get the neutral "Known gaps".

**How it surfaced.** Adding the panel's assertions to the sibling smoke tests (NYC #78, SF #43) printed the section labels, and the label for a fork with no outlines was visibly wrong. Nothing failed — the assertions check the section *count*, which was correct — so this is a case where writing the test found the bug by making the behaviour legible, not by going red.

The distinction is worth stating because it recurs: an engine block written against the reference fork's data shape can be *correct there* and *misleading elsewhere*. The guard is to ask what the block claims when the fork-specific input is empty. Here the input is `counties`, and empty means "cannot answer", not "answer is none".
